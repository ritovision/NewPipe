## Evidence levels

| Level | Meaning in this review | What it does not establish |
| --- | --- | --- |
| I — inspection | Actual implementation, migrations, tests and history read and traced by this reviewer. | Runtime behavior on every supported platform. |
| B — build only | Retained build/artifact metadata; current app/test APK hashes independently recomputed. | Any test executed merely because it compiled. |
| L — local execution | Node/JVM or disposable SQLite/Miniflare execution. Retained suite results are marked retained; new probes are marked review-executed. | Android lifecycle, deployed CPU or live provider behavior. |
| N — native instrumentation | Retained Android runner results using real native stores. A fake peer remains a fake even on Android. | Live Cloudflare, independent hardware or power-loss durability. |
| H — live HTTP/Cloudflare | Retained deployed HTTP/operator/Android-to-Cloudflare results at specified checkpoints. | Final-candidate coverage for routes not exercised, or an unlimited resource guarantee. |
| U — unverified | No sufficient executed evidence for the specified composition/boundary. | An automatic defect finding; missing coverage and actual defects are separate. |

Confidence below means confidence in the stated, bounded assessment, not a probability of being defect-free. “Gap confirmed” means the evidence demonstrably does not cover the asserted property.

## Review-executed tests and their limits

### Disposable SQLite ordering probe

Two process-exit cases reproduced the witness/baseline mismatch. It used ordinary SQLite WAL transactions in separate temporary databases, with the same commit order and recovery predicate as the code. It did not instantiate Android Room, Keystore, WorkManager or the real TagRepository. It demonstrates why the source ordering is unsafe; native regression is still required.

### Disposable Miniflare cancellation probe

Three invocations each tested RESERVED and UPLOADING. The first established the HTTP failure; the second counted DATA statement dispatch; the third added all current DATA migrations. All used current production modules with a temporary existing-harness adapter. Each invocation reports two failed first-response expectations and successful exact retries. The counter adapter does not bypass the production budget/fence path. This is local workerd/D1/R2 execution, not a mock-only test, but is still not deployed Cloudflare.

### Not executed by this review

No build, full backend/JVM rerun, Android test or installation, force-stop of an app, Wi-Fi change, live HTTP call to QA/production, migration, provider restore, archive mutation, credential action, policy change, cron activation or deployment occurred. Public provider/Android documentation was read to verify API semantics; those documentation lookups are not application traffic.

## Evidence weaknesses that matter

- A passing test suite does not establish **composition** of independently tested recovery components. The preserved-old-generation archive path is the clearest example.
- A fake remote peer can exercise native transaction semantics while missing the real HTTP route's authentication, fence and statement overhead. The cancellation reproduction exposes that distinction.
- A same-generation older-revision archive test does not test service-generation recovery.
- A one-time test beginning OFF does not establish the ON-to-OFF postcondition.
- Rotation of one dialog does not cover sibling dialogs, and visible synthetic summary rows do not prove complete large-diff browsing.
- Exception injection is not process death; process death is not storage/power failure. The five retained reconnection kills are useful precisely because their boundaries are named and their scope is explicit.
- The earlier failed CPU samples (12.181 and 8.692 ms p95) remain retained. The final 6.950 ms result is a legitimate measured improvement, but thirty head-heavy requests provide limited statistical and route coverage.
- Some synthetic native fixtures still use cache directories despite the checkpoint's cache-fixture remediation. The successful 157-test log is valid evidence; it should not be described as proof that every fixture/staging path is immune to cache loss.
