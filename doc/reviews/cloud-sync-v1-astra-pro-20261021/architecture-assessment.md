# Architecture and operational assessment

Implementation inspected: `1b7ab927a7840f3fc0e0b41cfd281199de77a6c8`.

## 1. Architectural judgment

Cloud & Sync v1 has a defensible separation of responsibilities. Ordinary synchronization transports a bounded declarative catalog through D1. Native Room/tag stores remain the app's installed data. Explicit R2 archives serve recovery and protected cloud replacement. An external CONTROL database owns maintenance admission and conservative project budgets so restoring DATA does not rewind the authority used to decide whether DATA may be touched.

This is substantial machinery, but most of it serves a real failure boundary: two native databases cannot share a Room transaction; DATA and R2 do not have a common commit; a provider restore can rewind DATA receipts; Android can die after a remote write; and an owner must be able to keep local edits detached from cloud. Removing journals, receipts, high-water marks or the external fence would not simplify the same safety contract.

No reviewed defect requires replacing this architecture. The serious problems are **cross-component contracts**: Forget orders its two commits differently from reconnection; archive reconstruction preserves a generation that the Android consumer refuses; and a native restore verifies an original archive while installing separately staged files whose inventory can change. These are major correctness gaps in the integrated feature, even though their corrections can be localized. See [ASTRA-CS-001–003](findings.md).

Primary design references: [cloud-sync-v1](../../architecture/cloud-sync-v1.md), [cloud-budgets-v1](../../architecture/cloud-budgets-v1.md), [cloud-operator-recovery](../../architecture/cloud-operator-recovery.md), [v1 specification](../../specs/cloud-sync-v1.md).

## 2. Components and trust boundaries

| Boundary | Authority and invariant | Assessment |
| --- | --- | --- |
| User choice → Android controller | A connection is not enrollment. OFF, enabled sync, one-time restore, recovery backup and shared-cloud replacement have different consequences. | Mostly explicit controls; ASTRA-CS-004 and 006 violate mode-transition requirements. |
| Native editors/AI/cloud → native databases | Shared writer coordination, verified Library/Unavailable identities, typed operations and exact preconditions protect existing app data. | Strong structure; the cross-store journal is necessary. Forget bypasses its safe cleanup ordering. |
| Android filesystem → confirmed candidate | The bytes and semantics approved must be the bytes/semantics installed; stale/missing staging must not change the operation. | Cloud transfer files are durably identified. Prepared native archive inventory is insufficiently bound (003). |
| Android → public Worker | HTTPS, device-scoped token, pinned service/library identity, bounded payloads and no raw SQL authority. | No bypass found in the inspected paths. A client failure state must still stop futile automatic traffic (006). |
| Public Worker → CONTROL → DATA | Reserve bounded work and obtain an external fence ticket before token SQL or ordinary DATA activity. | Correct placement; external durability survives DATA rollback. A long composed route fails to complete within the cap (005). |
| DATA → R2 | A READY index entry must refer to the exact verified immutable archive. Unknown object operations must not be declared safely absent. | Explicit multipart/rotation/quarantine state machine is appropriate. Live final-ledger coverage remains incomplete. |
| Operator → external fence/provider/DATA | Separate operator authentication and exclusive action ownership; inspect actual resources, not a client's asserted plan; recover with fresh authority. | Meaningful guard chain, with availability costs for genuinely unresolved operations. |
| Recovered generation → old archive | New authorization protects access to immutable historical content; old provenance must not become new authority. | Current producer/consumer contracts disagree (002). |
| Housekeeping → retained evidence | Cleanup may prune bounded terminal data without lowering high-water or deleting pinned/uncertain recovery state. | Purposefully limited capability and cursor-based work are sound. |

## 3. Catalog model and feature completeness

The catalog uses exact service/URL media keys and portable IDs for mutable entities instead of assuming native integer IDs or matching names across devices. Canonicalization, fingerprints and shared wire vectors make a whole-catalog comparison meaningful. Library membership is unique; ordinary playlist occurrence order and duplicates remain meaningful. Categories, tags, assignments, display order and Unavailable state are represented explicitly. Display metadata is treated as hints rather than remote SQL authority. Sources: [CloudCatalog.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudCatalog.kt), [CloudIdentityStore.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudIdentityStore.kt), [CloudNativeCatalog.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudNativeCatalog.kt), [CloudPages.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudPages.kt), [catalog.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/catalog.ts), [pages.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/pages.ts).

Whole-catalog optimistic concurrency is a reasonable v1 choice. The controller compares local state, an acknowledged baseline and the remote head; concurrent divergence pauses for explicit resolution. Automatic merging of unrelated device edits is deliberately not promised. Preserving a dirty local branch through conflict is more important here than maximizing automatic convergence. The retained live matrix establishes the small-fixture push/pull and conflict flow, including duplicate/tag/Unavailable content, but not all multi-device schedules.

The exact-preview design is stronger than a summary-only confirmation: it freezes identity, fingerprints, remote head and candidate; confirmation checks for changed local/remote state; a local safety copy precedes destructive catalog reconciliation. These guards should survive the fixes. The explorer has two small defects: Unavailable ordering is not rendered (007), and a recovery search filter becomes invisible after rotation (008). They do not invalidate all existing previews, but they contradict an unqualified “every change discoverable” claim.

One-time backup and shared-cloud replacement are appropriately separated. The latter needs an outgoing-cloud archive and explicit replacement authority because it changes other devices' source of truth. A normal device ZIP backup does not need to modify the shared catalog or toggle ongoing sync. The one-time current-cloud restore path, however, must implement its promised OFF postcondition even when entered from ON.

## 4. Native transaction boundaries and crash recovery

### Catalog apply

The normal apply path compiles a typed plan from a verified native snapshot, validates the serialized journal representation before mutation, persists intent in the side database, writes Room with a matching receipt, and reconciles the tag side according to that receipt. Recovery does not blindly replay destructive Room operations from a side journal. It checks incarnation, operation identity and target state before settling. This avoids the dangerous assumption that “an intent exists” proves the native deletion committed. Sources: [CloudApplyCompiler.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudApplyCompiler.kt), [CloudApplyPlan.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudApplyPlan.kt), [CloudApplyStore.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudApplyStore.kt), [CloudNativeApply.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudNativeApply.kt).

Native apply tests use real Room/tag stores and check more than final cloud fingerprints: the preservation of unrelated native records and mappings matters. Nevertheless, exception injection and re-opening a test helper are narrower than host process death. The five recent host kills cover **reconnection**, not every native apply boundary.

### Connection cleanup

A completed apply leaves a useful witness/baseline pair. Removing one before the other is itself a cross-database state transition. Reconnection correctly commits witness removal first. Forget reverses that ordering by nesting an independent tag transaction inside a Room transaction. The isolated SQLite reproduction demonstrates that this can manufacture the exact lost-journal state that recovery must reject (001).

The remedy should preserve the recovery guard and use consistent ordering/idempotence. Merely ignoring a leftover witness would turn a detectable inconsistency into possible unverified native recovery. Persisting OFF first also prevents a crash during forgetting from preserving an active automatic connection.

### Full native ZIP restore

The native importer performs important protections: recognized ZIP entry names, bounded expansion/counts, duplicate-known-entry refusal, supported schema checks, staged migrations, integrity/foreign-key checks, rejection of executable schema, runtime-authority scrubbing, writer draining, WAL checkpoints and a recoverable file-swap journal. Restore deliberately freezes old helpers and requires restart. A normal sync does not invoke this full replacement/pairing-reset path. Sources: [TagBackupCoordinator.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/tagging/TagBackupCoordinator.kt), [CatalogFileSwap.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/tagging/CatalogFileSwap.kt), [CatalogOpenHelperFactory.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/tagging/CatalogOpenHelperFactory.kt).

Those safeguards protect a chosen set of files; they do not prove that the chosen set is still the approved one. Prepared tag/settings/binding files live under cache, and later existence checks conflate “absent from the original input” with “lost after validation.” The file swap can therefore atomically install a substituted pair (003). Correctness requires a frozen inventory and final integrity admission, not a more elaborate swap algorithm.

SQLite-owned export snapshots require SQLite 3.27 or newer in this implementation. Older engines explicitly refuse, as documented in [tagging-production](../../architecture/tagging-production.md). The release must name its supported snapshot/device scope; failing closed on an older engine is preferable to taking unsafe raw WAL copies, but compilation against the app's minimum SDK is not proof that every backup-dependent cloud action works there.

## 5. Remote publication, retries and competing devices

Public SQL is compiled from typed, bounded operations and uses prepared parameters. Final write batches assert device/library/service/auth generation, revocation/write authority, sequence and exact base head; they atomically update catalog pages, accepted head, receipt and resolved-sequence high-water. Checking authorization again in the committing transaction is essential because an earlier successful status call does not reserve authority. Sources: [admission.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/admission.ts), [service.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/service.ts), [index.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/index.ts).

Immutable upload identity and exact receipt/digest matching distinguish an idempotent replay from a changed operation. Retiring a sequence fences delayed publication; absence of a receipt alone is not taken as permission to reuse an identity. Keeping the resolved-sequence high-water after old receipts are pruned prevents a stale client from becoming “new” again. Ordered chunk/page hashes and canonical fingerprints constrain malformed or partial payloads.

Cloudflare documents D1 batches as transactional, with failure rolling back the batch: [D1 batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/). The reviewed code relies on that boundary, not on an atomic transaction across a phone, DATA, CONTROL and R2. When a write's result is ambiguous, retaining its durable identity and external hold is the conservative response.

The replacement cancellation defect is an integration cost issue, not a failure of this basic publication transaction. Nested catalog/recovery cleanup consumes its 27 DATA statement allowance before completion, then the recovery wrapper labels a known pre-dispatch refusal as unknown. The repeat operation succeeds because retirement/ABORTING state is durable and idempotent. Correct either the query composition or the explicit progress protocol without increasing the public ceiling casually.

## 6. Authorization, credentials and hostile input

No server authorization bypass was established. Device authority is scoped to configured service/library and current auth generation; replacement additionally requires an internal grant and verified outgoing archive tied to the incoming approval. Request JSON does not supply an arbitrary trusted SQL program. Operator actions use separate authentication and resource identity checks. The operator re-inspects/regenerates the guarded work; a local plan seal is an integrity aid, not sufficient authorization by itself. Sources: [admission.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/admission.ts), [replacement-state.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/replacement-state.ts), [replacement.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/replacement.ts), [worker.mjs](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/operator/worker.mjs), [recovery.mjs](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/operator/recovery.mjs).

The Android client uses a private HTTPS client without redirects/shared cookies/logging interceptors, bounds reads and validates response formats. Credentials are encrypted through Android Keystore and stored outside the exported catalog/runtime databases. The credential dialog uses password input, disables saved state and sets screenshot protection before presentation. The retained UI assertions support those specific controls. This review does not claim protection against a rooted device, arbitrary code in the same app UID, or loss/invalidation of the Keystore key. Sources: [CloudHttpClient.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudHttpClient.kt), [CloudConnectionStore.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudConnectionStore.kt), [CloudSyncSettingsFragment.kt](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/app/src/main/java/org/schabi/newpipe/settings/CloudSyncSettingsFragment.kt).

Native ZIP provenance is not equivalent to trust. The server can verify bounded container bytes/manifests, while Android must validate the actual native schema and content before installation. The importer rejects triggers/views before opening a staged database for migrations; it also checks expected structure and foreign keys. That is a meaningful defense against executable archive schema, not simply trust in a producer-validation string.

Permanent token rejection is secure at the server but incomplete as an Android lifecycle transition. Leaving enabled true preserves periodic/native-change traffic forever. A generation-conditional paused/OFF transition fixes that without discarding unknown uploads or other evidence (006).

The current safety limits reduce resource abuse but are not a complete denial-of-service boundary. Many rejected requests can still consume Worker/CONTROL work, and an authenticated device can consume its project's admitted budget. This is an availability and operational scope limitation already acknowledged by the budget design; no unsupported absolute anti-abuse guarantee should be made.

## 7. Daily budgets and performance

### What is enforced

The policy targets **2,000,000 reads/day**, **50,000 writes/day**, **250,000,000 DATA bytes**, and **32 SQL statements/public request**. CONTROL owns policy, spent/held counters and unresolved reservation records. Admission is before DATA token authentication. Concurrent reservations occur in a guarded transaction, with estimated growth held before dispatch. A nonexpiring ticket prevents maintenance from overtaking an uncertain request. DATA restore does not reset this ledger. Sources: [budget.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/budget.ts), [fence.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/fence.ts), [0003_budgets.sql](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/control-migrations/0003_budgets.sql).

The D1 wrapper observes result metadata for all supported operations; `first()` is implemented through measured `all()` so it does not drop usage metadata. Whole batches are checked against the statement allowance before dispatch. The observed DATA size high-water and growth holds are conservative; cleanup or restored older DATA does not refund historical capacity automatically. Missing/corrupt policy or unavailable/invalid result metadata fails closed rather than manufacturing a zero charge. [D1 result metadata](https://developers.cloudflare.com/d1/worker-api/return-object/) documents the row/size fields this implementation uses.

UTC rollover retains unresolved holds. Settlement can itself roll the ledger day, and tests challenge admission/settlement around midnight. These tests establish the local accounting algorithm; they do not prove exact reconciliation with provider billing windows for every asynchronous request. Charges include conservative allowances for CONTROL admission/settlement and index costs.

### What is not guaranteed

An estimate is checked against real result metadata **after** a database operation has executed. If underestimated, the triggering operation can already have consumed more than estimated before later work is refused and the circuit blocks admissions. Growth has the same limitation. Missing metadata or uncertain results retain capacity rather than safely refunding it, trading availability for safety.

Operator recovery uses its own bounded maintenance reservations/statement policy rather than pretending it is a 32-statement public request. Emergency authenticated CONTROL-only closing, manual provider administration, historical activity and repeated rejected traffic are not an absolute account-wide billing cap. The documented starting debit for prior administrative activity is appropriately conservative, but it does not turn unmetered activity into perfectly known provider usage.

Accordingly, the implementation provides reasonable **application-level safety limits for the admitted profile**. They should continue to be described that way. ASTRA-CS-005 shows a valid route cannot finish within its allowance; it does not show that the allowance is bypassed.

### CPU evidence

The retained final minified sample supports a reported p95 of 6.950 ms, under the 8 ms target, over 30 requests. Earlier p95 failures of 12.181 and 8.692 ms are preserved rather than erased. The final sample contains 26 head requests and only four other small requests; no chunk/seal/publication or R2 mutation path is measured in that public window. The six operator cleanup passes are separate activity.

There is therefore sufficient evidence for “this small head-heavy deployed sample met the target,” and insufficient evidence for “all v1 operations on the final candidate meet it.” The actual raw analytics response/query and deployed bundle identity should be retained next time to make source-to-measurement attribution and percentile verification stronger. A representative small-profile mutation/recovery sample is a release gate, not a request to repeat already useful unit tests.

## 8. External recovery and archive lifecycle

The fence transitions serve different purposes: OPEN admits ordinary work; DRAINING stops new admission while existing tickets settle; HELD permits exclusive maintenance only after the necessary emptiness/ownership checks. An unknown public request or RUNNING action cannot be erased because it is old. The external action record must remain meaningful while DATA may be restored or its index rebuilt. Sources: [fence.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/fence.ts), [worker.mjs](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/operator/worker.mjs), [reopen.mjs](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/operator/reopen.mjs).

Operator recovery independently inventories and verifies R2 objects, checks scope and stored provenance, rebuilds the DATA index transactionally, records a receipt, revokes old authority and prepares fresh generation/device credentials before reopening. Current CONTROL upgrades test rollback when the gate is open/draining, tickets/actions remain or historical ownership cannot be mapped. The review found no reason to discard those guards.

The three-slot archive state machine has distinct reservation, rotation, upload, verification, READY, abort and quarantine phases. Existing copies are not simply deleted to “make room” without an approved rotation and survivor checks. Immutable keys/digests and object identity checks matter because an index row alone does not prove the object still exists. Unknown creation/abort outcomes are deliberately retained for operator reconciliation.

The main systemic defect is at the consumer: preserved A-generation archive bytes are valid historical content, but the current Android apply model uses their head as if it had to be current B-generation authority. The correction should preserve historical provenance while representing the local result as an explicitly restored/divergent branch, not a fabricated acknowledgement of the current cloud head. New credentials and current highest-observed counters must remain authoritative; next enrollment remains explicit.

Indefinitely unresolved provider operations can leave a service unavailable. That is an honest consequence of uncertainty, not evidence that it is safe to expire tickets. The runbook should clearly identify when authoritative provider evidence or a fresh-resource recovery is necessary. No speculative force-clear procedure is recommended.

## 9. Housekeeping and long-term operation

Housekeeping is intentionally smaller than operator recovery. It advances a bounded device cursor, limits eligible stage/receipt work, preserves active/referenced stages and unknown R2 operations, and does not hold an archive-mutation capability. Receipt retention uses an observed eligible prefix age, retains recent receipts and the sequence high-water, and pins current replacement references. These choices avoid resurrecting old requests when storage is reclaimed. Sources: [housekeeping.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/housekeeping.ts), [housekeeping-schedule.ts](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/src/housekeeping-schedule.ts), [0006_housekeeping.sql](https://github.com/ritovision/NewPipe/blob/1b7ab927a7840f3fc0e0b41cfd281199de77a6c8/cloud/migrations/0006_housekeeping.sql).

The local tests cover racing publication versus cleanup, large receipt histories, integer limits, revocation/expiry and missing schema. Retained live checks cover active-stage preservation, retirement, terminal cleanup and high-water survival. A scheduled trigger is implemented and gated through ordinary admission, but no cron is active or live-tested. That is an explicit deployment condition, not a reason to activate it during review.

Cursor bounds and conservative retention can leave old data around for some time. That is acceptable if operators understand progress/capacity and the process remains bounded. A future dashboard or richer progress display would help, but is not a release blocker in this review.

## 10. Android lifecycle and remaining operational limits

The scheduler uses constrained periodic work, exponential backoff and debounced native-change wakeups. App startup installs it and restores durable enabled state; controller generations protect stale requests/apply after disable. The retained live outage/restart matrix is meaningful evidence for basic offline persistence and automatic reconnection. It remains one emulator with two packages, and therefore does not establish separate-device clock/network behavior, OEM background restrictions, Doze latency or battery use.

The inspected wiring does not show a dedicated foreground-resume refresh hook beyond startup/reconcile/native-change events. Confirm the intended foreground-latency promise or narrow the documentation. This is recorded as a follow-up acceptance/documentation gap, not a fabricated corruption finding.

The final retained QA state is intentionally closed: HELD revision 15, public and housekeeping flags false, zero outstanding work/holds, six revoked credentials and three READY archives totaling 4,995 bytes. This review made no live state changes and offers no activation authorization. The next technical step is to fix the bounded defects, test their actual component boundaries, and select a corrected candidate for separately authorized integrated acceptance.
