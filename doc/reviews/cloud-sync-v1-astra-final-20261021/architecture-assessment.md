# Complete-system architecture assessment

Reviewed source: **`2b5c85b801481923de9af88aaa082868db40cd92`**, `feature/cloud-sync-v1-20261019`.

**The design is suitable to enter final integrated verification. No broad redesign is genuinely necessary.** The complexity largely corresponds to real independent commit domains: Room, the tag database, private files, D1 DATA, R2, and external CONTROL. Replacing this with an in-memory lock, timeout-based reclamation or an implicit cross-store transaction would remove safety rather than simplify an equivalent guarantee.

The governing requirements are the [approved specification](../../specs/cloud-sync-v1.md), [architecture](../../architecture/cloud-sync-v1.md), [budgets](../../architecture/cloud-budgets-v1.md) and [operator recovery contract](../../architecture/cloud-operator-recovery.md). This assessment follows their whole-catalog, explicit-conflict and explicit-recovery product model; it does not require CRDT merge, new infrastructure or a different consent model.

## 1. Authorities and trust boundaries

| Domain | Authority and commit point | Boundary that must not be crossed implicitly |
| --- | --- | --- |
| Native catalog | Installed Room/tag contents, protected Library/Unavailable identities and database incarnation | A cloud ID or matching display name cannot adopt arbitrary native rows. A record sync cannot replace preferences, history or AI authority. |
| Local connection/outbox | Keystore-protected token, durable connection generation and frozen operation bytes | An obsolete generation cannot admit later networking/apply. OFF prevents automatic work while explicit one-time operations remain available. Current local edits cannot be substituted into an old request. |
| D1 DATA | Guarded transactional publication of catalog, head, receipt and device high-water | Preflight authentication alone cannot authorize the final commit. A missing response cannot be treated as rollback. |
| R2 | Immutable archive key, byte digest/manifest and verified provider identity | An index row or metadata claim alone cannot prove exact archived bytes; an uncertain multipart must continue to occupy capacity. |
| CONTROL | Durable admission tickets, budget reservations, external service/fence state and exclusive operator actions | DATA restore cannot rewind this authority. A timer, local detach or client-provided plan cannot release an unknown effect. |
| Operator | Separately authenticated, narrowly scoped recovery/reopen actions checked against actual deployed authority and inventory | Ordinary device credentials cannot mint authority, submit SQL, perform Time Travel or bypass maintenance. |

The public router fixes the library/service/resource from configuration, validates exact request fields and bounds, and admits a metered ticket before DATA token lookup. Tokens are derived to a device hash and reasserted in write guards; redirects and browser-origin use are refused. See [index.ts:61–191](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/index.ts#L61-L191), [service.ts:419–429](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/service.ts#L419-L429) and [admission.ts:100–159](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/admission.ts#L100-L159).

Recovered-service reconnection requires a different service generation, same library and a fresh zero-sequence device. Explicit rejected-device detachment archives local evidence and locally forbids reuse of that retired device identity. Provisioning must continue to issue per-installation credentials; sharing one credential across installations is not a supported concurrency model. See [CloudSyncController.kt:65–144](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudSyncController.kt#L65-L144) and [CloudConnectionStore.kt:170–241](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudConnectionStore.kt#L170-L241).

## 2. Native data integrity

### Record apply is a recoverable two-store protocol

The essential invariant is that Room's committed result determines whether side metadata may finish; a pending plan is not permission to replay the destructive Room phase.

Capture validates persisted role bindings, incarnation and native identity high-water under the existing writer barrier. Compilation maps portable IDs explicitly, preserves protected roles, preserves playlist duplicates/order and permanent artwork, and refuses unreviewed orphan-tag displacement. Before effects, the plan is encoded and decoded through the same bounded persisted format. The tag journal commits first; the Room transaction writes native changes and the matching witness together; only then are tag contents, mappings and baseline completed. See [CloudNativeCatalog.kt:59–161](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudNativeCatalog.kt#L59-L161), [CloudApplyCompiler.kt:25–155](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudApplyCompiler.kt#L25-L155) and [CloudNativeApply.kt:49–118](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudNativeApply.kt#L49-L118).

Recovery proves the journal checksum/context and inspects the witness. An absent witness allows abandoning an uncommitted plan only after proving the original native/tag state. A matching witness authorizes completion of the tag phase, with exact native projection and tag-revision checks. A contradictory witness, missing plan or modified projection blocks rather than guessing. The Room mutations are never replayed during that completion. See [CloudNativeApply.kt:197–313](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudNativeApply.kt#L197-L313).

Ordinary apply updates only the relevant local playlist/membership and tag domains. It preserves stream/history/progress records and remote bookmarks; cloud display hints do not overwrite existing stream metadata. Explicit preview can authorize displacement of recoverable orphan assignments after a safety backup, while automatic apply refuses such a conflict. Tag/category name swaps use temporary names to preserve stable identities. These details matter because “same final fingerprint” would not by itself prove preservation of unrelated native state.

Forget, reconnect and rejected-device detach remove the Room witness before independently deleting its side baseline. The inverse order would recreate the original persistent mismatch. Detachment's final clean-identity exception is narrow: it first recovers native state, permits an absent cloud context after legitimate import, and rejects a different extant identity. See [CloudSyncController.kt:129–232](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudSyncController.kt#L129-L232).

### Full ZIP restore is a different operation

A native ZIP can replace the full native stores and optionally preferences. It therefore retains explicit restart/AI-unpair behavior; ordinary sync does not use that path. Preparation bounds entry count, decompressed bytes, names and database sizes, validates SQLite/schema/integrity, sanitizes cloud/AI executable authority, and retains the exact post-validation file inventory. Expected absence is part of the candidate. Cache eviction cannot silently turn a full import into a tagless stock import. See [TagBackupCoordinator.kt:52–181](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/tagging/TagBackupCoordinator.kt#L52-L181).

Quiescence stops AI admission and drains work outside the TagRuntime lock without persisting unpairing. Final candidate, generation and preview checks run under the barrier, followed by lease commit, native freeze and unpairing. A semantic/inventory refusal before commit resumes current durable policy. After commit, a drain/checkpoint or filesystem failure remains an irreversible restore attempt requiring restart; the code does not pretend to roll back pairing. The file-swap journal recovers the complete old or committed-new set and validates the chosen set before copying it. See [TagBackupCoordinator.kt:220–288](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/tagging/TagBackupCoordinator.kt#L220-L288), [AiControlRuntime.kt:480–552](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/aicontrol/AiControlRuntime.kt#L480-L552) and [CatalogFileSwap.kt:1–182](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/tagging/CatalogFileSwap.kt#L1-L182).

Export uses consistent SQLite snapshots, validates/sanitizes them and verifies each member while streaming the ZIP. A failed output is not promoted over the local recovery ZIP. Process-owned staging cleanup is restricted to orphan temporary imports/exports, excluding outboxes, the retained safety ZIP and file-swap journals. See [TagBackupCoordinator.kt:290–345](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/tagging/TagBackupCoordinator.kt#L290-L345), [CloudSyncController.kt:563–581](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudSyncController.kt#L563-L581) and [NativeCatalogStaging.kt:1–67](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/tagging/NativeCatalogStaging.kt#L1-L67).

The retained native tests and actual process kills substantiate these mechanisms. They do not prove power-loss behavior on every filesystem or the full corrected live-provider/native composition.

## 3. Synchronization, conflicts and consent

The application maintains both an acknowledged cloud baseline and a highest observed head. Equal semantic content can adopt an authenticated baseline. Local-only changes push; cloud-only changes pull with local safety protection; divergent branches pause for review. Scope changes and decreasing/reused head identities stop automatic work. Historical source provenance never becomes a current-service acknowledgement. See [CloudSyncPolicy.kt:1–100](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudSyncPolicy.kt#L1-L100) and [CloudApplyStore.kt:35–100](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudApplyStore.kt#L35-L100).

The outbox is frozen durably before the first request. Its persisted header, chunk hashes, generation and incarnation are revalidated on load. A retry uses the same sequence and digest. Definitive stale/expired refusals invoke resolve-or-retire, where an already COMMITTED receipt wins. The client validates sequence, digest, scope and target fingerprint before acknowledging or clearing. Network/unknown outcomes retain their identity; the retry does not swallow later local edits. See [CloudTransferStore.kt:12–107](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudTransferStore.kt#L12-L107) and [CloudSyncController.kt:402–518](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudSyncController.kt#L402-L518).

Disable linearizes at the durable generation change under the shared native barrier. It cannot unsend an already issued request, and the code preserves that operation's evidence. Old callbacks lose local admission. One-time confirmation ends OFF even if preparation began ON; preview/cancel alone does not change mode. Replacement preserves the owner's toggle while an unresolved replacement marker blocks automatic work. Final admission binds local semantic state, tag revision, orphan state, native identities and remote head/manifest rather than only a UI preview ID.

WorkManager is appropriate to the specified non-instant background behavior. Unique work and network constraints coalesce events; periodic polling discovers remote-only changes. Removing the `streams` observer avoids capture on metadata/history/feed-only invalidation while retaining semantic triggers. Actual Room invalidation and WorkManager tests support the wiring. Independent devices, Doze/OEM timing, longer offline periods and writer-barrier latency still need measured acceptance. See [CloudScheduler.kt:35–123](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudScheduler.kt#L35-L123).

## 4. Catalog transaction and malformed-input discipline

Catalog pages are a bounded storage representation of a validated semantic catalog. Packed rows avoid a write per membership occurrence. Both implementations validate identity, ordered memberships, references, canonical pages and semantic fingerprints; golden vectors cover the language boundary. The server reconstructs and validates the full target before sealing, then commits only the immutable sealed identity.

The final publication assertion covers current token hash, auth generation, service generation, revocation/write permission, exact base head and next sequence. Receipt/high-water and catalog mutation share the same D1 batch. Replacement adds the current grant, database-time expiry/cooldown and exact outgoing archive proof. Concurrent devices therefore cannot both publish from one shared base. See [service.ts:193–399](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/service.ts#L193-L399) and [admission.ts:100–159](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/admission.ts#L100-L159).

This relies on D1 transactional batch rollback, consistent with the official [D1 batch contract](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), checked during review on 2026-10-21. It does not rely on an isolate mutex.

The uncertainty classifier intentionally recognizes only the exact assertion CHECK failure as a known rollback. Consequently client-influenced constraints must be rejected before a later UNIQUE/CHECK violation. The cross-chunk guard now proves global ordering before insertion. The independently executed malformed-header/chunk probes also establish that bounded bad input does not consume permanent CONTROL capacity and does not prevent a valid continuation. This is concrete evidence for the current schema, not an exhaustive proof for every conceivable future mutation.

## 5. Three-slot archives and whole-cloud replacement

All reserved, incomplete, deleting and quarantined work counts against the three-slot model. Rotation names the oldest eligible archive, rechecks the required verified survivors and confirms absence before allocating the replacement payload. A stale replacement retry reuses its own slot under stricter survivor/attempt checks; it does not repeatedly evict history. See [recovery.ts:169–269](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/recovery.ts#L169-L269) and [recovery.ts:305–369](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/recovery.ts#L305-L369).

Every payload uses multipart, including small archives. Creation is claimed before a non-idempotent provider call. Lost identity is not permission to create another multipart. Parts are bound to manifest digests; complete resolves against authoritative head; verification checks streamed bytes and archive structure. Cloud-catalog archives bind the exact current source head and page manifest. Native-ZIP producer validation is supplemented by Android's real database validation on restore; server ZIP-boundary checks alone are not a SQLite restore certificate.

Cancellation separates known progress from uncertainty. Rotation, abort claim, durable consumption proof and final absence/removal fit separate bounded requests. `abort_fenced` prevents a normal continuation from repeating a successful abort. The terminal SQL guard still requires current operation/slot identity and proof. Concurrent quarantine cannot be erased by stale claim progress. A crash or lost provider response before durable proof remains uncertain.

The official [R2 Workers API contract](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) distinguishes constructing a multipart handle from proving that its upload still exists. This review does not assume that a repeated abort succeeds; the local provider shim deliberately rejects that case. Real R2 behavior and corrected route CPU remain acceptance obligations.

Replacement cannot publish incoming local pages as their own outgoing safety archive. Final SQL requires a DONE backup, READY exact source archive and current manifest/provider identity before advancing epoch/head. Retiring an unadmitted intent fences delayed reservation/publication, and cancellation retains completed history. See [service.ts:322–381](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/service.ts#L322-L381) and [replacement.ts:60–170](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/replacement.ts#L60-L170).

## 6. External recovery and operational safety

CONTROL is outside the DATA rollback domain. Admission creates non-expiring tickets before access to DATA/R2. Closing maintenance stops new admissions and reaches HELD only after all tickets and running actions are absent. A request cannot release its ticket while a tracked effect is pending or uncertain, and cannot start another effect through its closed wrapper. See [fence.ts:1–118](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/fence.ts#L1-L118) and [maintenance.ts:1–46](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/maintenance.ts#L1-L46).

Operator recovery independently checks deployed bindings/disabled gates, scope, fresh-resource provenance, the external fence, full completed/multipart inventories and bounded DATA snapshots. A client-provided seal does not make submitted SQL authoritative: the service reconstructs and compares the plan against actual state before claiming an exclusive action. Unknown provider restore/rebuild/reopen outcomes retain exclusivity. Reopening requires validated catalog/archives, fresh authority and durable DATA enrollment evidence before the external OPEN transaction. See [recovery.mjs:134–238](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/operator/recovery.mjs#L134-L238), [reopen.mjs:1–90](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/operator/reopen.mjs#L1-L90) and [worker.mjs:64–145](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/operator/worker.mjs#L64-L145).

Rebuild preserves catalog receipts and device high-water records while revoking old devices and retaining original archive provenance. A fresh receiving generation can use an old same-library catalog through explicit local historical restore. This is the central cross-component correction: immutable archive provenance, current authorization and local acknowledgement now have different representations.

The cost is availability. A genuinely unknown storage mutation can permanently prevent safe in-place recovery; there is no supported forced expiry. Local detachment preserves unresolved evidence but cannot release remote holds. Operational plans must respect this limit and retain independent local exports. It is documented behavior, not a new reason to redesign or invent an unsafe “repair” endpoint.

## 7. Resource envelope

The implementation enforces the agreed application safety policy through CONTROL reservations and conservative settlement:

| Target | Mechanism and assessment |
| --- | --- |
| 2,000,000 project rows read / UTC day | Indexed CONTROL reservation before token SQL; measured reads plus accounting allowance on settlement; unknown holds carried through rollover. |
| 50,000 project rows written / UTC day | Atomic write reservation; actual indexed-write metadata; full estimate charged for known rollback with unreported work; unknown capacity is not refunded. |
| 250 MB DATA maximum | 250,000,000-byte policy ceiling, measured database-size high-water plus concurrent growth holds. |
| 32 SQL positions / public request | Whole batch checked before dispatch; five accounting positions reserved. Phased cancellation preserves the ceiling. The separate bounded operator envelope is not presented as a public route allowance. |
| 8 ms deployed p95 CPU for admitted small profile | A measured release gate, not something proved by type checking, Miniflare or row reservations. Current representative mutation/recovery evidence is still required. |

See [budget.ts:10–171](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/budget.ts#L10-L171) and `cloud/control-migrations/0003_budgets.sql`. Missing/invalid D1 metadata or an underestimated reservation blocks further admission instead of silently refunding capacity. Repeated settlement is not used to recover from a lost settlement reply. Current-day holds survive UTC rollover and DATA rewind. The focused 32-case execution tests these branches.

These are application limits, not absolute Cloudflare billing guarantees. They apply to the admitted resource policy; additional active resource pairs require an explicit aggregate project allocation. Rejected traffic, emergency control and administrative/provider operations need the documented operational accounting margin. This report does not assume unlimited parallel pairs each receive the full project allowance.

Housekeeping is bounded, opt-in, uses ordinary admission and has no R2 capability. It guards stale-stage retirement, preserves sequence high-water and referenced receipts, and ages a fixed observed receipt prefix rather than newly advanced receipts. Retained QA evidence records cron disabled; current live state was not queried. See [housekeeping.ts:4–76](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/housekeeping.ts#L4-L76) and [housekeeping-schedule.ts:7–16](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/cloud/src/housekeeping-schedule.ts#L7-L16).

Large catalog captures hold a native writer transaction; page efficiency does not remove that phone-side cost. The small deployed profile, realistic native-ZIP size and acceptable writer latency must remain explicit rollout constraints.

## 8. Security, diagnostics and UI

Android keeps token ciphertext and all cloud runtime state under no-backup private storage, uses Keystore AES-GCM with destination/device/scope-bound authenticated data, and does not recreate a missing key to “decrypt” old bytes. Transport disables redirects, automatic retries, cookies and credential logging, bounds requests/responses and checks generation during streaming. Exports strip cloud executable state. Operator diagnostics sanitize error types/frames instead of emitting token-bearing exceptions. See [CloudConnectionStore.kt:21–140](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudConnectionStore.kt#L21-L140), [CloudHttpClient.kt:1–145](https://github.com/ritovision/NewPipe/blob/2b5c85b801481923de9af88aaa082868db40cd92/app/src/main/java/org/schabi/newpipe/custom/cloud/CloudHttpClient.kt#L1-L145) and `cloud/operator/worker.mjs`.

The UI retains candidate/filter state in activity models, not token-bearing saved-state bundles. Credential entry is transient, password-masked and screenshot-protected before display. Exact change groups are searchable and pageable; Unavailable order is disclosed. Recovery/replacement summaries name rotation consequences and distinguish local full restore from record apply. Historical light/dark/black landscape images show readable native surfaces and reachable actions; this is historical screenshot inspection, not current UI execution.

## Conclusion

The corrected system has defensible commit points, current transactional authority, exact receipt/candidate identity and conservative handling of provider uncertainty. The remaining work is a bounded integrated acceptance phase with the corrected client/server pair and measured operational profile. There is no source-backed reason in this review to introduce a broad redesign or another general review cycle.
