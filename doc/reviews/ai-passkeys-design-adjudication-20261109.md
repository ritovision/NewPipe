# AI passkeys design review — implementation adjudication

Date: 2026-11-09. Scope: the approved [passkeys/durable authorization specification](../specs/ai-control-passkeys-durable-auth.md). Source: [independent Astra Max read-only review](ai-passkeys-design-astra-max-20261109.md). These are implementation requirements, not claims of completed or deployed behavior.

## Accepted requirements

1. **Authoritative browser-session revocation.** Store opaque owner-session identity, credential ID or recovery authentication type, owner epoch, absolute expiry and CSRF state in durable storage. Validate on privileged use and at authorization commit. Logout invalidates the server session; removal invalidates that credential's sessions; explicit recovery/security reset can advance the owner epoch. Reject legacy stateless portal cookies rather than importing their authority. This may require signing into the portal again; existing Android pairings and OAuth grants remain unchanged. Invalidated sessions cannot authorize pending registration, consent or pairing.
2. **Purpose/action-bound verification.** Challenges bind owner, browser/session, operation/target, configured RP/origin and deadline. Consume once at an atomic commit that rechecks session/credential/epoch validity. New-passkey registration proves possession of the *new* key, not ownership: adding/removing credentials also requires fresh existing-passkey or recovery-key verification. Use one-use action-bound authorization where necessary. Last-passkey removal requires deliberate fresh recovery-key verification; it must not accidentally lock out the owner. Synced zero-counter passkeys must work without relaxing challenge replay protection.
3. **Explicit, single-use OAuth consent.** Preserve original provider consent transaction/cookie, immutable request details and S256. Require explicit `decision=allow`, not merely absence of deny. Add session-bound, transaction-specific CSRF and durable single-use consumption. Login returns to consent rather than auto-approving. Logging out/revoking invalidates pending consent; signing in again cannot silently resurrect it. Claim the grant operation before provider issuance; ambiguous failures must not reopen it for replay. Keep destructive scopes unchecked and existing scope ceilings.
4. **Browser-origin checks distinct from native APIs.** New credential/session/consent browser POSTs require exact Origin and CSRF/binding, not the existing helper that permits missing Origin for native clients. Preserve authorized native device API compatibility. Server-configured HTTPS origin and exact hostname determine WebAuthn origin/RP ID; do not accept either from submitted data. Keep Android DER/SPKI device verification separate from WebAuthn.
5. **Pairing transcript and comparison.** Versioned signatures bind operation, origin, device ID/key, local nonce, transaction and immutable details. Identical begin retries do not extend expiry. Status/finish prove the original key. The browser requires explicit visual comparison against a short code/identity shown by the live app-initiated request; no copying/typing a pairing secret is required. Names/URL data alone are not proof of local initiation. This reduces approval-link phishing, not a claim of app attestation.
6. **Pairing commit and crash recovery.** Use separate pending-pair records, <=5-minute lifetime and explicit states. Existing `devices[].pending` is retry bookkeeping, NOT a security quarantine. Register a DeviceRoom only after approved signed finish commits. Recheck deadline, key, approver/session/epoch and cancellation at the commit. Identical completion retries recover the same result, never re-enroll a revoked device. Avoid cross-object waits under the account gate; define recoverable post-commit registration retries.
7. **Preserve working Android state.** Stage new pairing separately from active configuration and keep pending state out of backups. Cancellation, timeout, backgrounding, restore, failed persistence and late callbacks must not destroy a working identity, change permissions, or enable the service. Match completion to the entire locally initiated transaction before replacement, not just a syntactically valid owner UUID. Continue to require explicit Start AI Control.
8. **Local assets, bounded storage and tests.** Bundle exact-pinned WebAuthn browser code locally; CSP permits only the necessary same-origin script/connect/form actions. Bound and prune challenges/sessions/credentials/pending requests, integrate existing alarm cleanup, and exercise real cryptographic verification in synthetic tests. Recheck revocation at commit, including concurrent requests. Browser, Pixel and live ChatGPT validation are separate from headless tests and must be recorded separately.

## Clarifications

- Ninety days means no **successful OAuth refresh**, not no human interaction. A host that refreshes unattended may keep a grant alive. The gateway cannot infer whether the owner personally used ChatGPT.
- The one-hour browser admin session is independent of the OAuth grant and device/service availability.
- Passkey/session removal does not implicitly revoke already-issued OAuth grants or Android devices. Those retain explicit, separately scoped revocation controls.
- Existing dedicated gateway hostname is retained for production RP identity; no new public domain, identity provider, or Cloud & Sync account migration is planned.
- These requirements supersede underspecified details of the original design, not its user-visible goals. The source-only reviewer did not validate current runtime/library behavior; implementation and independent regression review must do that.
